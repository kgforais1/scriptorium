# Plan: M1.5 PDF import

Last reviewed: 2026-11-07

Author: planning pass (branch `plan/m15-pdf-import`)
Status: in-progress
Linked issue/PR: n/a
Roadmap: [M1.5 — PDF import](2026-08-23-product-roadmap.md#m15--pdf-import)

## Goal

Let a curator turn a PDF into a book. Each PDF page becomes a display image that the existing
reader shows unchanged. The PDF itself is kept once as an original, so nothing is lost. Any text
the PDF carries is saved for M2 search. Readers get books from the most common digitised format.
Curators no longer have to rasterise PDFs by hand before importing.

## Out of scope

- OCR, search UI, and the hidden text layer. Those are M2. This plan stores plain PDF text only.
- Word and line boxes for PDF text. The PDF original is kept, so M2 can extract boxes from it
  when it builds the text layer. Doing it now would add the riskiest coordinate mapping to a
  milestone that does not use it.
- Picking a single `.pdf` file in the dialog. Ingest takes a folder (`create.rs:409`), and a
  folder holding one PDF works. A file picker is a small follow-up.
- Showing PDF pages as vectors, or re-rendering at a higher zoom. Pages are raster images, like
  every other book.
- PDF annotations, forms, links, outlines, and attachments.
- Password-protected or encrypted PDFs. They are refused with a clear message.
- Running pdfium in a separate process. The risk is recorded below.
- A `formatVersion` bump. v2 already has `sources[].format = "pdf"`
  (`book-format.v2.schema.json:219`) and a per-page `frame`, and the text goes under `ocr/`,
  which is outside `meta.json`.

## Approach

A PDF becomes one more multi-frame input, like a multi-page TIFF. A PDF in the picked folder is
one source with `frames` equal to its page count. Each frame becomes one page, in order, mixed
with any images in the folder by the existing sort.

### Rasteriser: pdfium through `pdfium-render`, loaded at runtime

`pdfium-render` (MIT or Apache-2.0) binds to a pdfium shared library at runtime. The app bundles
one prebuilt pdfium library from
[bblanchon/pdfium-binaries](https://github.com/bblanchon/pdfium-binaries), pinned to one
release. We use the build without V8 and XFA, so no PDF JavaScript can run.

- `scripts/fetch_pdfium.sh` downloads the pinned archive for the **host platform only**. It
  checks a SHA-256 recorded in the script, and unpacks the library into one flat, gitignored
  directory, `src-tauri/pdfium/`. Dev, tests, CI, and release all use it.
- Each bundle carries only its own platform's library. The base `tauri.conf.json` stays as it
  is. Tauri 2's platform config files (`tauri.macos.conf.json`, `tauri.windows.conf.json`,
  `tauri.linux.conf.json`) each add one resource entry for that platform's library name. Phase
  1 confirms that `resources` merges this way and does not replace the base list. If it
  replaces it, each platform file repeats the three notice files.
- At startup the app loads the library by an absolute path in the resource directory. Tests
  read `PDFIUM_DYNAMIC_LIB_PATH` and fall back to `concat!(env!("CARGO_MANIFEST_DIR"), "/pdfium")`,
  so a local `cargo test` works with no export. In CI the fetch step runs under `shell: bash`
  (the Windows default is PowerShell) as `../scripts/fetch_pdfium.sh`, because the Rust jobs
  default to `working-directory: src-tauri`. It also writes the variable to `$GITHUB_ENV`.
- If the library is missing or fails to load, PDF ingest fails with a clear error. Image ingest,
  reading, and loading existing PDF books still work (see `load_book` below).
- Tauri runs commands on a thread pool, so two ingests can overlap. pdfium is not thread-safe.
  Enable `pdfium-render`'s `thread_safe` feature, which serialises every pdfium call behind a
  global lock. Phase 1 checks the crate's real feature names before fixing `Cargo.toml`.

### Fitting into `convert.rs`

- `sniff` accepts `%PDF-` anywhere in the first 1024 bytes. Readers such as Acrobat tolerate
  leading junk there, so some valid PDFs do not start at byte 0.
- `pdf.rs` holds the one `Pdfium` instance in a `OnceLock`, bound at startup or on first use.
  It loads documents with `load_from_path`, not from `Source.bytes`, so there is no
  self-referential struct. The checksum still comes from `Source.bytes`. A file swapped between
  that read and pdfium's open is the same narrow window images already have, and `load_book`
  checks the frame count later.
- `open` must special-case `Pdf` before `needs_display_conversion` (`convert.rs:216`), whose
  `decode::header_info` cannot read a PDF. `converted_ext` and `passthrough_ext`
  (`convert.rs:84-98`) are exhaustive matches and need a `Pdf` arm (`"jpg"` in both).
- `open` for `InputKind::Pdf` opens the document once through pdfium. It records the page count
  as `frames`, sets `needs_conversion = true` and `display_ext = "jpg"`, and refuses an
  encrypted PDF, a PDF with zero pages, and a truncated file.
- `Source` keeps the open pdfium document for a PDF, so `frame()` renders from it and never
  goes through `decode_frame`. `add_input` re-opens each input after `inspect_all`
  (`create.rs:325`). That costs a second pdfium open per PDF, but it is cheap next to rendering,
  so we keep the existing flow and the `Inspection` equality check.
- `Source::page_text(frame) -> Option<String>` returns a PDF page's text, and `None` for an
  image. `add_input` (`create.rs:337`) calls it next to `frame()`, so the builder gets the text
  without touching pdfium itself.
- `frame()` for a PDF renders the page to an RGBA bitmap. It flattens the bitmap onto white,
  so any transparent area becomes paper, not black. It then drops alpha, giving `Rgb8`, which
  is already sRGB. It then calls the existing private `encode`, from inside `convert.rs`.
  `color::to_srgb8` is skipped, because pdfium renders in sRGB.

### Rendering rule (normative for M1.5)

- pdfium applies the page's `/Rotate` and crop box when it renders. The rule uses the rotated
  crop-box size in points.
- The render size starts at 300 DPI. It is then scaled down, keeping the aspect ratio, until the
  long edge is at most 4000 px and the area is at most 12 MP. Pages are never rendered above
  300 DPI.
- Each page renders with annotations off, flattened onto white, and stored as a JPEG at
  `JPEG_QUALITY` (92).
- A page whose size rounds below 1 px on either side is `UnreadableFile`.

### Errors

`open` and `frame` return `ConvertError` (`convert.rs:102`), which `create.rs:122` maps to
`BookError`. Add `ConvertError::EncryptedPdf` and `ConvertError::PdfiumUnavailable`, and map
them to the matching new `BookError` variants. `TooManyPages` is raised in `create.rs` directly.
Each new `BookError` needs a `Display` arm (`library/mod.rs:83`), an entry in
`command_error.rs`, and an update to the variant-count test there (`command_error.rs:130`).
The `NoSupportedImages` message (`library/mod.rs:90`) becomes "no images or PDFs".

### Text

For each page with text, ingest writes `ocr/<NNNN>.json` with `source: "pdf"` and the page's
plain text. It writes no boxes. `ocr/index.json` uses the reserved shape in
[`docs/book-format.md`](../docs/book-format.md#reserved-layout-for-page-text-and-annotations-provisional):
a `pages` map from page position to a per-page `status`, an `engine` of `pdfium`, and
`generatedAt`. A PDF page with text gets `status: "text"`. A PDF page without text gets
`status: "none"`. Image pages are not listed. The book-level rollup is a `summary` object with
`pdfPages` and `withText` counts. A book with no PDF pages gets no `ocr/` files at all. It
keeps the empty `ocr/` directory that ingest already creates (`create.rs:249`), and `finish()`
validates `ocr/` only when it wrote something. Page files are named with
`numbered(index, page_count)` by book page position, not by a count of text pages.

`book-format.md` today names only the fields (`status`, `engine`, `generatedAt`, a rollup), so
Phase 2 writes these exact values into it first. The layout stays provisional until M2. A short
JSON schema, `docs/ocr.v0.schema.json`, covers the two files. `finish()` validates them before
the rename with an `include_str!` validator, the same way `load.rs:16` embeds the book schemas. `load_book` does not read `ocr/` yet. M2 will add
boxes to the page file, and its schema becomes v1 then.

### `load_book`

`load_book` checks a PDF original's page count against `frames` when pdfium is loaded. When it
is not, it falls back to today's checksum-only check (`load.rs:213`) and logs that once.
Without that fallback, a missing library would make every PDF book unreadable.

### Free space

`estimate_bytes` gives a PDF a per-frame display budget of 12 MB, not the 6 MB
`DISPLAY_FRAME_ESTIMATE` (`create.rs:177`). A noisy 12 MP page at q92 can pass 6 MB, and a
vector PDF's bytes per page say nothing about its rasters. It also adds 64 KB per frame for
`ocr/` text. The free-space rule in `book-format.md` is unchanged, because `estimated_bytes`
already means everything ingest writes.

### Limits

- The total page count, PDFs plus images, must stay at or below the schema's 100000
  (`book-format.v2.schema.json:75`). Ingest checks this before rendering, so the error comes
  at once, not after hours.
- `total_frames` (`create.rs:191`) sums into a `u32`. It becomes
  `Result<u32, BookError>` with a checked sum, and its two callers change with it:
  `Builder::new` (`create.rs:255`) and `inspect_folder` (`inspect.rs:76`).

### Alternatives considered

| Option | Why not chosen |
|---|---|
| MuPDF (`mupdf` crate) | AGPL. It is incompatible with shipping under PolyForm Shield. |
| pdf.js in the webview | It rasterises on the frontend, so ingest, checksums, and the atomic write would split across two runtimes. It is slower for big books, and harder to test in Rust. |
| `hayro` or another pure-Rust renderer | It has no C to bundle. But it is young, and its font and colour fidelity on old scanned PDFs is unproven. Revisit if pdfium bundling hurts. |
| Build pdfium from source | It needs the Chromium toolchain on every CI runner. |
| Poppler (`pdftoppm`) sidecar | GPL. It is also an external install on Windows. |

## Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| A hostile PDF crashes pdfium in-process and takes down the app | low | high | Use the no-JS build and pin a recent release. Follow the bump policy. A sidecar is the follow-up if it happens. |
| pdfium has no NVD CPE, so `check_bundled_c_cves.py` cannot track it | high | med | Keep it out of `bundled-c.toml`, which is for crates that vendor C. Follow the bump policy instead. |
| A missing or mismatched library on a user's machine | med | med | Ship it per platform as a resource, load it by an absolute path, and fail only PDF ingest. Existing PDF books still load. |
| Tauri replaces the base `resources` list instead of merging it | med | low | Phase 1 checks this. If it replaces, each platform file repeats the notices. |
| The free-space estimate is too low for a noisy PDF | low | med | Use a 12 MB per-frame budget, the existing 10% headroom, and the atomic temp-dir write. |
| CI time grows from the download | low | low | Cache the archive by version. It is about 5 MB. |
| Large PDFs make the import slow | med | low | The existing progress events count frames. |
