## Goal

Retire the **page-turn library risk** before M1 book I/O. Produce a committed **ADR** and a
throwaway prototype proving we can show **heterogeneous scan images** with a real page-turn
metaphor inside Tauri’s webview under React StrictMode. If the metaphor cannot work, stop and
ask the product owner — do **not** silently ship an image strip.

## Out of scope

- Book package ingest / `meta.json` I/O (M1)
- OCR, library UI, hotspots
- Production polish / paper texture

## Why this exists

`page-flip` / `react-pageflip` last published ~2022. StPageFlip requires fixed `width`/`height`
for the whole book; real scan folders are often non-uniform. Canvas `loadFromImages` does not
support hard pages (affects later M7). React 18+ StrictMode double-invokes effects and breaks
many 2021-era imperative wrappers. These are blockers for M1 as previously written.

## Approach

Time-box **1–2 days**. Allowed outcomes (all valid):

| Outcome | When |
|---|---|
| Keep StPageFlip / `page-flip` as-is | Spike passes all gates below |
| Vendor/fork `page-flip` and patch | Small fixes unblock us; document fork path |
| Switch to a named alternative | Evaluate in order: (1) HTML-mode StPageFlip with per-page sized HTML, (2) thin CSS 3D transform own-build (~300 lines), (3) only if needed — another inventory candidate after a 1-hour survey |
| Own CSS/WebGL page-turn | Libraries fail; owner accepts cost |

**Search bound:** do not spend more than ~2 hours evaluating unnamed libraries. Prefer fork or own CSS 3D over open-ended shopping.

**Forbidden:** silent fallback to a non-flip `<img>` strip. If only that works, ADR says
“blocked — need product decision.”

### Aspect-ratio policy (must pick one in ADR)

| Policy | Meaning |
|---|---|
| **Pad-to-uniform** | Letterbox/pillarbox pages to one book ratio (derived from page 1 or max box) — preferred default for “faithful content, shared stage” |
| **Per-book ratio from page 1** | Reject or warn on pages outside tolerance (e.g. >5% aspect delta) |
| **Reject non-uniform** | Ingest fails if pages disagree beyond tolerance |

“Faithful” for M1 means: **no stretch/distort**; padding/letterbox OK; source pixels not cropped
except optional trivial edge trim documented later.

## Phases & checklist

### Phase 1 — Prototype corpus

- [ ] Build a tiny fixture set (gitignored under `tmp/` or generated by script): ≥3 pages with
      **deliberately different** aspect ratios + one ~200-page synthetic JPEG corpus for load smoke
- [ ] Document how to regenerate fixtures (committed script → writes into `tmp/`)

### Phase 2 — Integrate candidate in Tauri + React

- [ ] Mount candidate under React 18/19 **StrictMode**
- [ ] Load local files via Tauri asset protocol / `convertFileSrc` (absolute paths)
- [ ] Exercise canvas vs HTML mode if using StPageFlip; note hard-page implications for M7
- [ ] Confirm turn animation works with keyboard next/prev

### Phase 3 — ADR

- [ ] Write `docs/adr/0001-flipbook-library.md` (or next free number) covering:
  - Chosen library (and version / fork URL if vendored)
  - Canvas vs HTML (or N/A)
  - React version pin + StrictMode result
  - Aspect-ratio policy
  - Known limits (max pages smoke-tested, memory notes)
  - Explicit non-outcome: no strip fallback

## Pass / fail gate (M1 may not start until pass)

| # | Gate | Pass means |
|---|---|---|
| G1 | Metaphor | Page-turn animation visible for ≥2 pages (not a static strip) |
| G2 | Heterogeneous | Three mismatched-aspect scans display without stretch (policy applied) |
| G3 | StrictMode | No double-mount crash / blank book on remount |
| G4 | Asset load | Pages load from disk via Tauri asset URL on macOS (Windows noted if available) |
| G5 | ADR | Committed ADR answers all bullets in Phase 3 |

**On fail:** Status → `blocked` or `abandoned`; report to user; do not begin M1 Phase 1.

## Reader design input (added 2026-10-27)

Seven look-and-feel prototypes (A–G) live in [`design/mockups/`](../design/mockups/) (PR #54).
They are reference only, not code to adopt. The spike should measure the chosen page-turn
approach against them, especially the curl in G and F.

Consider supporting multiple skins from the start:

- One shared page-turn engine.
- Each skin is a data config: scene (wood, lighting, props, camera), book material
  (cover, paper, ribbon) and UI theme tokens.
- Swappable UI layouts (A-style toolbar vs B-style scrubber and panel) cost more; defer
  unless needed.
- Once a direction is picked, create `DESIGN.md` for shared principles and one token file
  per skin (W3C design-tokens JSON). The token files are the source of truth for each look.
